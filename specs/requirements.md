# 英雄联盟助手工具 - 需求文档

## 概述

开发一款英雄联盟助手工具，首期专注于 PC 桌面端，通过连接英雄联盟客户端（LCU API）提供战绩查询、排位信息查看等功能。架构设计预留扩展空间，以支持后续的用户系统、Riot API 集成、多平台适配等能力。

## 术语表

| 术语 | 定义 |
|------|------|
| **LCU API** | League Client Update API，英雄联盟本地客户端 API，随客户端启动在本地开放 |
| **Riot API** | Riot Games 官方远程 API，需申请 API Key，支持独立于客户端的数据查询 |
| **PUUID** | Player Universal Unique ID，玩家全局唯一标识 |
| **Summoner** | 召唤师，英雄联盟中的玩家角色 |
| **Electron** | 基于 Chromium 和 Node.js 的跨平台桌面应用框架 |
| **lockfile** | LOL 客户端启动时生成的文件，包含 LCU API 的端口和认证凭证 |
| **主进程** | Electron 的 Node.js 进程，负责系统级操作 |
| **渲染进程** | Electron 的 Chromium 进程，负责界面渲染 |

---

## 版本规划

### 首期（当前版本）

- **平台**: PC 桌面端（Windows）
- **数据来源**: LCU API（本地客户端）
- **架构**: 无后端，Electron 内嵌 Vue3 前端
- **核心功能**: 战绩查询、排位信息、召唤师信息、对局实时分析、选人助手

### 二期（预留扩展）

- **平台**: PC 网页端、移动端网页
- **数据来源**: Riot API（远程）
- **架构**: 引入后端服务（MidwayJS）
- **新增功能**: 独立于 PC 查询、用户系统、数据云端同步

## 需求列表

### REQ-001: 客户端连接与用户识别 [首期]

**用户故事:** 作为一名玩家，我希望工具能够自动识别当前登录的英雄联盟客户端，以便快速获取我的游戏数据。

#### 验收标准

1. WHEN 用户启动应用，系统 SHALL 自动检测本地运行的英雄联盟客户端进程。
2. WHEN 检测到运行中的客户端，系统 SHALL 读取客户端 lockfile 获取连接凭证（端口和认证 token）。
3. WHEN 成功获取凭证，系统 SHALL 建立 LCU API 连接并获取当前召唤师信息。
4. IF 客户端未运行，系统 SHALL 显示友好提示引导用户启动客户端。
5. WHILE 客户端连接中，系统 SHALL 在状态栏显示"已连接"状态及召唤师名称。
6. WHEN 客户端关闭或连接断开，系统 SHALL 自动检测并更新状态为"未连接"。

---

### REQ-002: 召唤师信息展示 [首期]

**用户故事:** 作为一名玩家，我希望查看当前登录账号的召唤师详细信息，以便了解我的账号状态。

#### 验收标准

1. WHEN 用户进入个人中心页面，系统 SHALL 展示召唤师头像、名称、等级。
2. WHILE 展示召唤师信息，系统 SHALL 显示当前段位、胜点信息。
3. WHILE 展示召唤师信息，系统 SHALL 显示历史最高段位记录。
4. WHILE 展示召唤师信息，系统 SHALL 显示经验值及升级进度。

---

### REQ-003: 战绩查询 [首期][核心]

**用户故事:** 作为一名玩家，我希望查看自己或对局中他人的历史战绩，以便分析游戏表现和改进方向。

**LCU API 限制说明:** LCU API 为本地客户端接口，查询他人战绩仅限于**当前对局中的队友/对手**（通过 gameflow session 获取 PUUID），不支持任意召唤师名称的开放搜索。开放搜索能力需二期 Riot API 支持。

#### 验收标准

1. WHEN 用户进入战绩页面，系统 SHALL 默认展示当前召唤师最近 20 场对局列表。
2. WHEN 用户在对局实时分析页点击某位玩家，系统 SHALL 展示该玩家的战绩列表（通过 PUUID 查询）。
3. WHEN 用户点击对局记录，系统 SHALL 展示该场对局的详细信息：
   - 英雄、KDA、造成伤害、承受伤害
   - 装备购买顺序、符文配置
   - 队友/对手信息及各自数据
   - 对局时长、击杀参与率、视野得分
4. WHEN 用户选择筛选条件（英雄、模式、时间段），系统 SHALL 根据条件过滤战绩列表。
5. IF 战绩数据较多，系统 SHALL 支持分页加载或无限滚动加载。
6. WHILE 战绩列表加载中，系统 SHALL 显示加载状态指示器。
7. WHEN 用户下拉战绩列表，系统 SHALL 刷新获取最新战绩数据。
8. IF 玩家无历史战绩（新号），系统 SHALL 展示空状态提示"暂无战绩数据"。
9. IF LCU API 返回数据不完整，系统 SHALL 展示可用字段并对缺失字段显示占位符。

---

### REQ-004: 排位信息查询 [首期]

**用户故事:** 作为一名玩家，我希望查看详细的排位信息，以便了解我的竞技水平和晋级进度。

#### 验收标准

1. WHEN 用户进入排位页面，系统 SHALL 分别展示单排/双排、灵活组排的段位信息。
2. WHILE 展示排位信息，系统 SHALL 显示当前胜点、胜场、负场、胜率。
3. WHILE 展示排位信息，系统 SHALL 显示晋级赛进度（如适用）。
4. WHILE 展示排位信息，系统 SHALL 可视化展示最近场次胜点变化趋势。

---

### REQ-005: 英雄数据统计 [首期]

**用户故事:** 作为一名玩家，我希望查看我各个英雄的使用统计，以便了解我的英雄池和熟练度。

#### 验收标准

1. WHEN 用户进入英雄统计页面，系统 SHALL 展示各英雄的使用次数、胜率、KDA。
2. WHEN 用户点击具体英雄，系统 SHALL 展示该英雄的详细数据：
   - 常用装备路线
   - 常用符文配置
   - 平均击杀/死亡/助攻
   - 平均游戏时长
3. WHILE 展示英雄列表，系统 SHALL 支持按胜率、使用次数、KDA 排序。
4. WHILE 展示英雄列表，系统 SHALL 支持按英雄名称搜索。

### REQ-006: 选人助手 [首期]

**用户故事:** 作为一名玩家，我希望在英雄选择阶段获得建议，以便做出更好的 BP 决策。

**数据来源（多层策略）:**
1. **第三方数据（主要）:** 通过爬取 OP.GG / Lolalytics 获取当前版本英雄胜率、克制关系、热门 Ban/Pick 数据。数据定期更新（每个游戏版本更新时刷新，或用户手动触发）。
2. **玩家个人数据（辅助）:** 结合玩家个人英雄池胜率数据（LCU API）进行个性化推荐。
3. **本地静态数据（兜底）:** 内置一份基础英雄克制关系表（JSON），当第三方数据不可用时作为兜底。

#### 验收标准

1. WHEN 用户进入英雄选择阶段，系统 SHALL 通过 LCU WebSocket 自动检测并进入选人助手模式。
2. WHILE 英雄选择中，系统 SHALL 基于第三方数据和玩家英雄池展示推荐英雄列表及推荐理由。
3. WHILE 英雄选择中，系统 SHALL 展示敌方已选英雄的克制建议（含克制胜率数据）。
4. WHEN 用户手动输入对局信息，系统 SHALL 提供阵容分析报告。
5. WHILE 选人助手运行，系统 SHALL 通过 LCU WebSocket 实时更新双方阵容变化。
6. WHILE 展示推荐数据，系统 SHALL 标注数据来源（"OP.GG"/"Lolalytics"/"本地数据"）和数据版本。

---

### REQ-007: 符文与装备推荐 [首期]

**用户故事:** 作为一名玩家，我希望快速获取英雄的推荐配置，以便在游戏中快速应用。

**数据来源（多层策略）:**
1. **第三方热门配置（主要）:** 通过爬取 OP.GG / Lolalytics 获取当前版本各英雄的热门符文和出装配置（含胜率、使用率数据）。
2. **玩家个人配置（辅助）:** 展示玩家自身历史战绩中的常用符文和出装（通过 LCU API）。
3. **内置默认配置（兜底）:** 当第三方数据和个人数据均不可用时，展示内置的基础推荐配置。

#### 验收标准

1. WHEN 用户查看英雄详情，系统 SHALL 展示该英雄的热门符文配置（含胜率和使用率）。
2. WHEN 用户查看英雄详情，系统 SHALL 展示该英雄的热门出装路线（含胜率和使用率）。
3. WHEN 用户查看英雄详情，系统 SHALL 同时展示玩家个人常用配置（如有）。
4. WHEN 用户点击"一键应用"，系统 SHALL 自动将符文配置应用到客户端（通过 LCU API）。
5. WHILE 展示推荐配置，系统 SHALL 标注配置来源（"OP.GG 热门"/"个人常用"/"默认推荐"）及数据版本。

---

### REQ-008: 对局实时分析 [首期][核心]

**用户故事:** 作为一名玩家，我希望在进入对局后能自动查看所有 10 名玩家的段位和近期表现，以便快速了解局势。

**触发时机与 REQ-006 的关系:** REQ-006（选人助手）在英雄选择阶段（ChampSelect）激活，REQ-008 在对局加载阶段（InProgress/GameStart）激活。选人阶段结束后，系统 SHALL 自动从选人助手视图过渡到对局分析视图。

**数据获取方案:** 通过 `/lol-gameflow/v1/session` 获取对局中 10 人基本信息（summonerId、championId），再并发请求每位玩家的段位（`/lol-ranked/v1/ranked-stats/{puuid}`）和英雄熟练度（`/lol-collections/v1/inventories/{summonerId}/champion-mastery`）。LCU API 对本地对局中的玩家数据查询无限制。

#### 验收标准

1. WHEN 游戏进入 Loading 阶段（通过 LCU WebSocket 监听 gameflow-phase 变为 InProgress），系统 SHALL 自动查询当前对局中所有 10 名玩家的信息。
2. WHILE 展示对局分析，系统 SHALL 显示每位玩家的段位、当前英雄胜率、近期战绩（近 10 场胜率）。
3. WHILE 展示对局分析，系统 SHALL 显示每位玩家该英雄的熟练度等级和使用场次。
4. WHILE 展示对局分析，系统 SHALL 用颜色标记对手实力水平（如高于/低于/接近自己的段位）。
5. WHEN 数据加载完成，系统 SHALL 自动将窗口置顶或发送系统通知提醒用户查看。
6. WHEN 用户点击对局分析中的某位玩家，系统 SHALL 支持跳转查看该玩家的详细战绩（REQ-003.2）。
7. IF 部分玩家的段位/战绩数据查询失败，系统 SHALL 对该玩家显示"数据获取失败"占位符，不影响其他玩家数据展示。

---

### REQ-009: 本地数据缓存 [首期]

**用户故事:** 作为一名玩家，我希望查询过的数据能够缓存，以便减少重复加载时间。

#### 验收标准

1. WHEN 用户首次查询战绩数据，系统 SHALL 将数据缓存到本地。
2. WHEN 用户再次请求相同数据，系统 SHALL 优先展示缓存数据并在后台检查更新。
3. WHEN 缓存数据超过各类型对应的 TTL（召唤师 5 分钟、战绩列表 2 分钟、战绩详情 30 分钟、排位 5 分钟），系统 SHALL 自动标记为过期并重新获取。
4. WHEN 本地缓存总大小超过 50MB，系统 SHALL 自动清理最久未访问的缓存条目。
5. WHEN 用户手动清除缓存，系统 SHALL 删除所有本地缓存数据。

---

### REQ-010: 窗口管理与通知 [首期]

**用户故事:** 作为一名玩家，我希望在游戏中也能快速查看助手信息，以便不中断游戏体验。

**全屏模式限制说明:** Windows 全屏独占模式下，任何 Always-on-Top 窗口均无法显示在游戏画面上方。窗口置顶和迷你模式仅在 LOL 设置为**窗口化或无边框窗口模式**时有效。应用 SHALL 在设置页提示用户将 LOL 设置为"无边框窗口"模式以获得最佳体验。

#### 验收标准

1. WHEN 用户开启"窗口置顶"选项，系统 SHALL 将窗口设置为 Always-on-Top。
2. WHEN 用户切换到迷你模式，系统 SHALL 将窗口缩小为悬浮小窗，仅显示关键信息（当前对局分析/选人建议）。
3. WHEN 游戏进入英雄选择阶段，系统 SHALL 自动激活助手窗口并发送系统托盘通知。
4. WHEN 对局结束，系统 SHALL 发送系统通知提醒用户查看本局数据，并自动刷新战绩。
5. WHILE 应用最小化到托盘，系统 SHALL 继续监听 LCU 事件。
6. WHEN 用户首次开启窗口置顶功能，系统 SHALL 提示"请将英雄联盟设置为无边框窗口模式以获得最佳体验"。

---

### REQ-011: 自动更新 [首期]

**用户故事:** 作为一名玩家，我希望应用能自动更新到最新版本，以便获取最新功能和修复。

**发布渠道:** 首期使用 **GitHub Releases** 作为更新分发渠道，electron-updater 配置 `provider: 'github'`。后续可切换为自建更新服务器。

#### 验收标准

1. WHEN 应用启动时，系统 SHALL 在后台检查是否有新版本（通过 GitHub Releases API）。
2. WHEN 发现新版本，系统 SHALL 在状态栏显示更新提示，用户可选择立即更新或稍后更新。
3. WHEN 用户确认更新，系统 SHALL 后台下载更新包并在下次启动时自动安装。
4. WHILE 下载更新包，系统 SHALL 显示下载进度。
5. IF 更新服务器不可达（网络问题），系统 SHALL 静默跳过本次检查，不影响正常使用。

### REQ-012: 首次启动引导 [首期]

**用户故事:** 作为首次使用的玩家，我希望有引导流程帮助我快速上手，以便了解工具功能并完成基础设置。

#### 验收标准

1. WHEN 用户首次启动应用，系统 SHALL 显示欢迎引导页面。
2. WHILE 引导流程中，系统 SHALL 引导用户确认 LOL 客户端安装路径（自动检测 + 手动指定）。
3. WHILE 引导流程中，系统 SHALL 简要介绍核心功能（战绩查询、选人助手、对局分析）。
4. WHILE 引导流程中，系统 SHALL 引导用户设置偏好（窗口置顶、迷你模式、LOL 无边框窗口模式提示）。
5. WHEN 引导完成，系统 SHALL 标记引导已完成，后续启动不再显示。
6. WHEN 用户在设置页点击"重新引导"，系统 SHALL 重新显示引导流程。

### REQ-016: 局域网访问代理 [架构预留]

**用户故事:** 作为一名玩家，我希望在同一局域网内的其他设备上访问工具，以便用手机查看 PC 端数据。

#### 验收标准

1. WHEN 用户开启局域网访问功能，系统 SHALL 启动本地代理服务器。
2. WHEN 其他设备通过局域网 IP 访问，系统 SHALL 提供 Web 界面。
3. WHILE 局域网访问开启，系统 SHALL 显示访问地址和二维码。
4. IF 安全风险较高，系统 SHALL 提示用户并要求确认开启。

**扩展说明:** 此功能作为首期可选功能，架构层面预留接口。

## 非功能性需求

### 性能要求

1. 应用启动时间 SHALL 不超过 3 秒。
2. 战绩列表加载时间 SHALL 不超过 2 秒（本地缓存命中时不超过 500ms）。
3. 内存占用 SHALL 不超过 200MB（正常使用状态）。

### 安全要求

1. LCU API 凭证 SHALL 仅存储在内存中，不持久化到磁盘。
2. 本地缓存数据 SHALL 不包含敏感信息。
3. 局域网访问功能 SHALL 默认关闭，需用户手动开启。

### 可用性

1. 应用窗口 SHALL 设置最小尺寸为 1024x768。
2. 应用 SHALL 支持常用键盘快捷键（F5 刷新数据、Ctrl+W 关闭窗口、Escape 返回上一页）。
3. 应用 SHALL 支持窗口缩放，内容自适应调整。
4. 应用 SHALL 支持窗口置顶（Always-on-Top）和迷你窗口模式。
5. 应用 SHALL 支持最小化到系统托盘。

### 可靠性

1. 应用 SHALL 集成日志系统（electron-log），记录 LCU 连接状态、API 调用异常、应用错误等信息。
2. 日志文件 SHALL 自动按日切割，保留最近 7 天的日志。
3. 应用 SHALL 在设置页提供"导出日志"功能，便于用户反馈问题时提交日志。

### 可维护性

1. 前端代码 SHALL 采用模块化架构，便于后续抽取为独立 Web 应用。
2. API 调用层 SHALL 统一封装，便于后续切换数据源（LCU API / Riot API）。
3. 配置项 SHALL 集中管理，便于后续扩展。

## 技术栈

### 首期技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| **桌面框架** | Electron | 主进程 + 渲染进程架构 |
| **前端框架** | Vue 3 + TypeScript | 组件化开发 |
| **状态管理** | Pinia | 轻量级状态管理 |
| **构建工具** | Vite | 快速构建和热更新 |
| **UI 组件库** | Naive UI | 轻量、TypeScript 友好、主题定制灵活 |
| **本地存储** | electron-store | 本地配置和缓存持久化 |
| **HTTP 客户端** | Axios | API 请求封装 |
| **数据爬取** | Cheerio | 第三方数据源 HTML 解析（OP.GG / Lolalytics） |
| **日志** | electron-log | 应用日志记录 |
| **自动更新** | electron-updater | 应用自动更新 |

## 技术决策记录

### TDR-001: 为什么首期不引入后端

| 项目 | 内容 |
|------|------|
| **决策** | 首期采用纯 Electron 架构，不引入后端服务 |
| **背景** | 用户首期仅需 PC 桌面端，无需跨设备同步 |
| **理由** | 1. 减少开发复杂度，快速交付<br>2. 无服务器运维成本<br>3. 数据在本地更安全 |
| **影响** | 后续扩展为 Web 端时需引入后端 |

### TDR-002: 为什么选择 LCU API 而非 Riot API

| 项目 | 内容 |
|------|------|
| **决策** | 首期使用 LCU API 作为数据来源 |
| **背景** | Riot API 有频率限制，且需要申请 Key |
| **理由** | 1. 无频率限制<br>2. 数据实时性更高<br>3. 无需申请 API Key<br>4. 可获取更多客户端特有数据 |
| **影响** | 需要用户打开 LOL 客户端才能使用 |
